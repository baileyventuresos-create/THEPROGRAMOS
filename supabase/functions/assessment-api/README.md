## What it is

The HTTP + auth boundary for the assessment workflow, hosted in the
Supabase project already chosen for The Program OS (TheProgramOS,
ref `rkgdwqgmldznczikrjip`). It exposes the same methods as
`server/assessment-api.js` over one POST endpoint:

```json
{ "method": "startAssessment", "params": { "athleteId": "<uuid>", "entries": [ ... ] } }
```

Methods (same role rules and error codes as `server/assessment-api.js`):
`listAthletes`, `startAssessment`, `recordAttempts`, `getDraft`,
`discardDraft`, `completeAssessment`, `athleteAssessmentView`,
`coachDashboard`, `recordDeferral`, `planReadiness`, `createPlan`,
`finalizePlan`, `advisoryPriorities`.

## Files

| File | What it is |
|---|---|
| `index.ts` | Deno entrypoint: CORS, JWT verification, auth-context + directory build, dispatch, error mapping. |
| `api.ts` | TypeScript port of the thin auth layer (`server/assessment-api.js`): the `ALLOWED` role table, `requireAuth`, parameter checks. No writes of its own. |
| `directory.ts` | Builds the auth context + access directory from the verified JWT, mirroring migration 003's RLS helpers (`app_role()`, `my_coach_id()`, `is_my_cohort_athlete()`, `is_my_athlete()`). |
| `store.ts` | PostgREST store adapters (assessment / reassessment / plan stores) with camelCase↔snake_case mapping. All queries run on the user-scoped client, so RLS applies. |
| `workflow.ts` | Seam that loads the bundled workflow (see §3). |
| `entry.mjs` / `build.mjs` | esbuild entry + script that generate `vendor/workflow.bundle.mjs`. Build artifact — not committed. |
| `config.toml` (in `supabase/`) | `[functions.assessment-api] verify_jwt = true` — platform-level JWT verification. |

## 1. Auth boundary

1. `config.toml` sets `verify_jwt = true`: Supabase verifies the JWT
   before the function is invoked.
2. `index.ts` calls `auth.getUser(token)` to resolve the JWT to a user.
   No request is processed without a verified user.
3. Role / coach / athlete mappings are read from the database
   (`app_users`, `coaches`, `athletes`), never from client input.
4. All data access uses the user-scoped client (the caller's own
   JWT). RLS (migrations 003 + 004) is the backstop. `service_role`
   is never used for user requests.
5. `actor` is always the auth UID; a client-supplied actor is ignored.

## 2. How the workflow runs here

The workflow logic is the tested Node code — `server/assessment-
workflow.js` plus its engine/battery/reassessment/gating/progress/
smart-draft modules. Those modules are CommonJS and only require
each other, so they bundle cleanly with esbuild into a single ESM
module (`vendor/workflow.bundle.mjs`, generated by `build.mjs`).
The function injects the PostgREST stores (`store.ts`) instead of
the Node memory/SQLite stores, and the access directory built in
`directory.ts`. No workflow rule changes; the same code, packaged
for Deno.

## 4. Known gaps — decide these before deploying (do not silently work around them)

1. **Workflow bundle is generated, not committed.** The function
   fails loudly (`WORKFLOW_BUNDLE_MISSING`) until `build.mjs` has
   run. The bundle must be generated and smoke-tested (see §5)
   before any deploy.
2. **`modified` / `capped` flags have no Postgres columns — until
   migration 005 is applied.**
   `server/assessment-store.js` records `modified` and `capped` on
   every assessment result, and `athleteAssessmentView` reads them
   back — but migration 002's `assessment_results` has neither
   column. `store.ts` maps them to `modified` / `capped` columns so
   the adapter works unchanged once they exist, but until migration
   005 (`server/migrations/005_unified_athlete_age_and_result_flags.sql`,
   written 2026-11-13, NOT applied) adds those two BOOLEAN columns,
   any insert/select touching `assessment_results` fails at
   PostgREST. Do not "fix" this by stuffing the flags into the
   `attempts` JSONB — attempts must stay the preserved numeric
   attempts.
3. **Adult athletes cannot be stored yet — until migration 005 is
   applied.** `athletes.age_years`
   is `CHECK (age_years BETWEEN 5 AND 19)` in migration 001, so an
   adult athlete (e.g. the 48-year-old validation case) cannot be
   an `athletes` row today. Migration 005 removes the 19 maximum
   (floor of 5 kept as a data-sanity guard) under the unified
   athlete system — one system for all ages, no divisions. The
   directory reports `age_years` as-is; nothing
   here works around the CHECK.
4. **IDs are UUIDs in Postgres, not Node `uid()` strings.** The
   Node stores generate ids like `asess_…`; Postgres id columns are
   UUID. `store.ts` assigns a fresh `crypto.randomUUID()` onto each
   row in place before inserting, so the caller's references stay
   consistent. No behaviour change — the workflow never exposes
   the id format to callers.
5. **Migrations 004 and 005 must be applied first.** The function reads and
   writes `assessment_schedules`, `assessment_deferrals`,
   `assessment_drafts`, `development_plans`, and the
   `idempotency_key` column, all of which 004 creates — and the
   `modified` / `capped` result columns and the relaxed athlete age
   CHECK, which 005 provides. Do not
   deploy before 004 and 005 are applied and verified (see
   `docs/MIGRATION_EXECUTION_PLAN.md`).
